# WeKan / COWORK integration — active work, not deployed

## Scope

The user authorized implementation and production deployment, then clarified that
the work-collaboration entry must be available to **all COWORK users**. There is no
per-firm enablement or designated first owner. The earlier first-owner question
is cancelled. Pearnly remains the login and ordinary employee-account authority;
WeKan retains its native site and board permissions. A WeKan role must never
grant a Pearnly owner/platform-admin role.

## Evidence and limits

- Six disposable real-PostgreSQL smoke tests passed: entry across separate firms
  and a personal user, one-time state binding, revocation, ordinary employee
  provisioning without privilege promotion, invitation scope/delivery failures
  and actual RLS cross-firm read/write isolation.
- Node cookie/header and AST installation tests passed; frontend build passed.
- Real local HTTP login/handoff returned the native WeKan HTML.
- External Chrome acceptance passed with a normal synthetic COWORK owner:
  regular login, left-menu handoff without a second login, Thai WeKan, private
  board creation, and native logout returning to COWORK. The user explicitly
  requested external Chrome after the in-app browser blocked the form.
- Browser acceptance exposed a real source-header defect: `no-referrer` makes a
  navigation POST send `Origin: null`. The handoff shell now uses `strict-origin`
  in its header and HTML, keeping the exact gateway origin check. See the
  [Fetch standard](https://fetch.spec.whatwg.org/#append-a-request-origin-header).
- The local full-app fixture boots schema separately and uses uvicorn with
  lifespan off because the snapshot lacks a legacy ERP database function.
  This is not evidence of complete production startup/readiness.
- Native DDP login, native admin UI-method issuance and REST issuance passed.
  Both kinds of issued employee log in at Pearnly with ordinary employee roles.
- Native readOnly can read a board; list creation and self-promotion are denied.
  A list-write denial uses HTTP 200 with a JSON 403, and readback proved no write.
- Cross-identity Authorization/X-Auth-Token/authToken/access_token requests are
  rejected. Native account disable closed an existing connection in 0.02 seconds;
  Pearnly logout closed it in 4.97 seconds and subsequent HTTP access was denied.
- Production MongoDB initialization was tested in a separate disposable
  container: the application can write only its database, admin access fails,
  and anonymous reads fail. The full production compose and backup restore are
  not yet accepted.
- Native invitation email used only a local SMTP sink restricted to example.test.
  Pearnly enrollment delivery was mocked after real DB scope checks; actual
  production delivery and password setup remain unverified.
- Final project gates and production deployment are still pending. Cloudflare
  login in external Chrome is awaiting the user's Google phone confirmation.
