## 一、这是什么 / 会计从哪进

### 侧栏路径

侧栏一个新的可折叠父栏「**使用教程**」(`nav-guide`),下面一个子栏「**Express 推送手册**」。
父栏定义在 `src/home/app-shell-sidebar-html.ts` 第 404–423 行,子项 `data-route="guide"`、
`data-gd-book="express"`;路由注册在 `src/home/route-table.ts`(`guide: 'loadGuidePage'`)。

层级是**侧栏只到手册这一层**。以后再写别的手册(比如 POS),就是「使用教程」下面多一个兄弟子栏,
手册内部的篇和章不占侧栏位置。页内是三层视图 + 面包屑:

- 手册首页:七张篇卡(不起面包屑,它自己就是首页)
- 篇页:该篇的章节列表(面包屑 = 手册名 / 篇名)
- 章节页:正文(面包屑 = 手册名 / 篇名 / 章名)

实现在 `src/home/guide-page.ts`(272 行),正文数据加载在 `src/home/guide-content.ts`(145 行)。

### 三处就地深链

比侧栏更要紧的是这三处。会计最需要教程的那一刻不是打开侧栏,是盯着一张推不进去的失败卡。
三处都埋了一个「**这是怎么回事**」按钮(文案键 `gd-why-link`),点了直达对应章:

| 位置 | 文件 | 行 |
| --- | --- | --- |
| 推送日志的失败卡(原因条旁边) | `src/home/erp-log-card.ts` | 301 |
| 推送详情抽屉的失败框 | `src/home/erp-log-detail.ts` | 232 |
| Express 推送就绪度「卡住」那一行 | `src/home/erp-express-detail.ts` | 222 |

映射表在 `src/home/guide-links.ts`(129 行):**35 个原因码 → 14 个章节 id**(我数过键,35 条;
去重后落到 14 个不同的章)。表里故意不收 `enqueue_error` 和 `payload_version_outdated`——
前者是系统异常(会计做不了任何事),后者靠小助手自更新解决,给它们挂教程只会把人引去一篇帮不上忙的文章。

## 二、为什么这么做

桌面上原来那份 POS 手册,Zihao 逐条判了四条死因。这次每条死因各对一个硬约束,不是「注意一下」,
是写进 CI 或者写进结构、绕不过去的东西。

| 死因 | 对应的硬约束 | 落在哪 |
| --- | --- | --- |
| **在产品外面** —— 一份放在外面的文档,没人找得到,也没人会去找 | 教程必须在产品里:侧栏一级入口 + 三处就地深链 | 侧栏 `nav-guide`;`guide-links.ts` 的 35 码映射;深链落空由 `check_guide.py` 闸④ 拦 |
| **讲功能不讲任务** —— 「XX 功能说明」这种标题,会计带着问题来,找不到自己那件事 | 125 章标题**一律动词开头的用户任务**,零条功能说明式标题 | 写作规约(非机械闸,见下方「闸的缺口」) |
| **太长啰嗦** —— 一章翻三屏,会计翻两下就放弃 | **一章一屏**:单章 steps ≤ 8 且中文正文 ≤ 900 字,超了 CI 红 | `check_guide.py` 闸③(`MAX_STEPS=8` / `MAX_ZH_CHARS=900`) |
| **图跟界面对不上** —— 手截的图三周后就是假的;中文正文配泰文界面图读者对不上号 | 图**全部脚本生成**,界面一改重跑即换新;中泰各一套,缺一不可 | `scripts/_guide_shots*.cjs`;`check_guide.py` 闸① 逐张核 `.zh.png` 与 `.th.png` 都在 |

「一章一屏」和「图两套齐」是机械可判的,做进了闸。「标题一律动词开头」目前**没有机械闸**——
这是已知缺口,靠写作时自觉和评审。要补的话,一条正则扫 `title.zh` 的首字就能拦大部分。

## 三、内容怎么产的

流程是这样的,顺序重要:

1. **代码穷举**。章节清单不是凭印象列的,是按代码里的枚举来:`erp_push_logs` 有几个 `status`
   就有几节,过账去向有几个选项就解释几个,预检 `reason` 有几种就覆盖几种。
2. **三路批判**。拿穷举出来的清单,从三个视角(会计真实使用、失败态、勘察文档)各跑一轮批判,
   合并去重后揪出 **46 条真缺口**。
3. **合并**成定稿清单。
4. **审计**:定稿清单逐条回代码验证,推翻站不住的条目(见下)。
5. **八路子代理撰写**:七篇 + 深链/闸各一路,并行写,各自留 `notes` 记下拍不了板的问题。

### 那条灾难级发现

批判揪出的 46 条里,有一条是灾难级的:

> **原清单有 8 章在教会计「点重试推送」,而那张卡上根本没有这个按钮。**

真相是:Express 的绝大多数拦截落在 `status='manual'`(待人工核对),而
`src/home/erp-log-card.ts:291` 的重试按钮渲染条件写死 `log.status === 'failed'`。
所以 manual 卡上不渲染重试按钮。会计唯一的自救路径是勾选那一行走批量重推,或者打开详情抽屉
(抽屉页脚的「重新推送」按钮只要有 `history_id` + `endpoint_id` 就渲染,后端
`routes/erp_push_log_routes.py` 的单条 retry 也只拒 `success`)。

也就是说:如果不审计就发出去,我们会交付一份**教人点一个不存在的按钮的手册**,
而且是在会计最慌的那一刻教。这 8 章全部改口重写,新开了 `exc-repush-how` 一章专讲「怎么重推」。

同一轮审计还推翻了几条批判自己站不住的前提(全部有代码位置为证):

- 「自动推送要 Plus 套餐、403」「端点数上限默认 1」「免费档静默不推」——
  `core/route_helpers.py` 的 `_plan_permissions` 已经彻底扁平化,忽略 plan、永远返回全开权限,
  那几条 403 分支是死代码。**没写「你的套餐不够」这一章**,改写成 `exc-nothing-in-log`
  讲真正会发生的三个成因。
- 「一个账号只能有一条 Express 连接」的真因是 `services/erp/push_schema.py` 上的
  `uq_erp_endpoints_user_express` 唯一索引,不是套餐限制。
- 「识别记录只保留 90 天」不准。可见窗口是 365 天;90 天只是没填字段时的兜底分支,而且到期不删数据。

**教训:批判也会过期。批判说的和代码说的冲突时,以代码为准,并把冲突记下来给 Zihao 拍板。**

## 四、图怎么产的

### 网页那 78 张(39 个图名 × 2 语)

四个脚本 + 一个共享库,职责切得很干净:

| 文件 | 行数 | 管什么 |
| --- | --- | --- |
| `scripts/_guide_shots.cjs` | 83 | **入口**。遍历语言 × 场景 × 图,调 `oneShot` 截图、计数、非零退出。不认识任何一张图的细节 |
| `scripts/_guide_shots_env.cjs` | 119 | **运行环境**。静态服务器(端口 8798)、假后端 `page.route('**/api/**')`、三种启动态(`boot` 已登录停在录入工作台 / `bootLogin` 登录页 / `bootGate` 套账硬门)。只管「把页面弄到可截的状态」 |
| `scripts/_guide_shots_list.cjs` | 306 | **图清单**。39 条截图定义:`id` / 选择器 / 所属场景 / 前置动作 `prep` / 裁剪 `clip` / 收尾 `after` |
| `scripts/_guide_shots_data.cjs` | 401 | **假接口数据**。按 URL 返回的假 JSON、假 OCR 结果、示例税票 HTML(渲成 PNG 喂给原图查看器)、主体列表 |

视口 1440×900,`deviceScaleFactor: 2`(2 倍图经得起放大;页面侧按 `naturalWidth/2` 还原显示尺寸)。
语言两套是外层循环 `LANGS = ['zh','th']`。

跑法:

```
node scripts/_guide_shots.cjs            # 全截
node scripts/_guide_shots.cjs upload-02-task overview-05-sidebar   # 只重截指定几张
```

产物落 `static/guide/shots/`,再由 `scripts/build-home-css.mjs` 的 `copyGuideAssets()`
复制进 `static/dist/guide-shots/` 随 dist 部署(vite `emptyOutDir` 每次清空,所以必须复制回去)。

**加一张新图的完整步骤:**

1. 在 `_guide_shots_list.cjs` 的 `SHOTS` 里加一条:`{ id: 'daily-12-xxx', sel: '.选择器', scene: 'wb' }`。
   要先点开某个抽屉/弹窗就写 `prep: async (page) => {...}`,要拼多块就写 `clip: ['.a', '.b']`(走 `unionClip`)。
2. 缺假数据就去 `_guide_shots_data.cjs` 补对应 URL 的返回。
3. `node scripts/_guide_shots.cjs daily-12-xxx` 单跑,确认两个语言各出一张、没有 `MISS`。
4. 在正文 JSON 的某个 step 上写 `"shot": "daily-12-xxx"`,`caption` 写就得中泰都写。
5. `python scripts/check_guide.py` 应该 PASS(它会核两套图都在)。
6. 重新 build,让图进 `static/dist/guide-shots/`。

## 五、闸

### `scripts/check_guide.py`(271 行,零依赖,只用标准库)

四道闸,查的都是「页面照样渲染出来、但读者会看到坏东西」的那类退化:

| 闸 | 查什么 | 不查会怎样 |
| --- | --- | --- |
| ① 配图存在 | 每个 `step.shot` 必须同时有 `<shot>.zh.png` 和 `<shot>.th.png` | 泰籍会计打开看到中文界面图,或者图是空的 |
| ② 双语齐全 | `title` / `intro` / `step.text` / `step.caption` / `note.text` 的 `zh` 与 `th` 都非空 | 缺 th = 泰籍会计看到中文;缺 zh = 中国会计看到泰文 |
| ③ 一章一屏 | 单章 `steps ≤ 8` 且中文正文(intro + steps + notes 合计)`≤ 900` 字 | 会计翻三屏就放弃,四条死因之一复辟 |
| ④ 深链不落空 | `guide-links.ts` 的 `REASON_CHAPTER` 里每个 (篇, 章) 都得真有这一章 | 点「这是怎么回事」退回手册首页,不白屏不报错——**深链等于没做而页面看着一切正常** |

另外两项清单校验:`index.json` 的 `planned` 不得小于该篇实际章数(防出现 `5/3` 这种倒挂进度);
章 id 全局唯一(深链按 id 找章,重了会命中错的那章)。还有一条:篇文件没登记进 `index.json` 的
`sections` 里 → 侧栏进不去,写了也没人看得到,也报红。

闸④ 读 TS 源用的是正则(`_LINK_TABLE` / `_LINK_ENTRY`)——为一张纯字面量表引整条 TS 工具链不划算。
先把行注释剃掉,免得注释里写的示例码被当成真映射。**关键一条:如果一条映射都没抠出来,闸会报红**
——表被清空或写法改了的时候,「全绿」正是它该报红的时候。

### 反证测试:`tests/unit/test_guide_gate.py`(388 行)

**实测 31 个用例,全绿**(用 `PYTHONIOENCODING=utf-8 python -m unittest tests.unit.test_guide_gate` 跑的)。

> ⚠️ 提交信息写的是「33 条反证测试」,**实际 31 条**。以实跑为准。
> 另外在这台机器上直接 `python -m unittest` 会报 3 个 error——那是 cp874 控制台编码炸的,
> 不是测试失败,**跑之前一定要设 `PYTHONIOENCODING=utf-8`**。

分三组:

- `GuideGateTests` 26 条:每一道闸都喂坏数据证明它抓得到。包括「整表指向占位 id 必须报红」
  (事故当天那张表)、「注释掉的映射不算数」、「表读不出来 = 闸失效 = 报红」、
  「篇还没开工不算故障」、「JSON 坏了要报出来不是抛异常」。
- `GuideGateExitCodeTests` 3 条:干净数据退 0、缺图退 1、死深链退 1。**闸的退出码本身也要验**
  ——这仓库栽过「闸接了管道把退出码吞了」。
- `RepoDataTests` 2 条:仓库里现有的真内容必须过闸、真映射表必须条条落到真章。

写法要点:**这仓库栽过「闸报绿其实闸根本没在看」,所以新闸一律先证明它抓得到坏数据。**
每条测试构造一份 fixture 目录(正文 JSON + 假 PNG + 假 `guide-links.ts`),故意破坏一处,
断言 `collect_failures()` 返回的违规里有对应那一条。

### 为什么独立成 `lint-guide` job

`.github/workflows/ci.yml` 第 144–163 行,是一个**独立的 job**,不是挂在 `lint-size` 底下:

```yaml
lint-guide:
  name: lint-guide (教程内容完整性 · 配图/双语/一屏 · FAIL mode)
  # 零依赖(只用标准库)· 任何环境跑得动
  - run: python scripts/check_guide.py
    env: { PYTHONIOENCODING: utf-8 }
```

理由写在 CI 注释里,值得抄一遍:**查的是「内容完整性」,和 `lint-size` 的「防大文件 / 防大 blob /
缓存破」不是一个轴。挂在那里会让教程里的一处笔误在 PR 检查列表上显示成 "anti-bigfile" 失败,
误导排查的人去翻文件行数。** 闸的名字就是给人看的第一条线索,别让它撒谎。

超时 5 分钟,零依赖(不装任何包),`FAIL` 模式——红了就挡合并。

## 六、踩过的坑

对接手最有价值的一节。每条都是现象 → 根因 → 怎么防的。

### ① 假绿的第三种形态:验收脚本用桩造了个不存在的东西来验自己

- **现象**:`_guide_deeplink_verify.cjs` **16 项全绿**,而 `guide-links.ts` 里 35 条深链
  **一条都落不到真章上**——表里全是 `stuck-no-revenue-account` 这类占位 id,真实内容
  `stuck.json` 里 42 章的 id 全是 `exc-*` 前缀。会计点「这是怎么回事」会全部降级回手册首页,
  不白屏、不报错,所以肉眼完全看不出来。
- **根因**:验收脚本自己用 `page.route` 桩注入了一个 `stuck-no-revenue-account` 章,
  然后验证「能跳到它」。**验收对象是脚本自己造出来的、产品里根本不存在的东西。**
- **这是假绿的第三种形态**,比前两种隐蔽:
  1. 闸压根没跑(钩子没挂 / 管道吞退出码)
  2. 闸跑了但扫错范围(diff 类闸在 commit 前跑,扫的是上一笔)
  3. **闸跑了、范围也对,但验收对象是 mock 出来的** ← 本条
- **怎么防的**:
  - E2E 里 mock 的边界要划清:**可以 mock 数据的内容,不能 mock 被验证的那个标识符。**
    造一张失败卡没问题,但卡上指向的章节 id / 路由名 / 错误码必须从真实产物里读出来喂进去。
  - 「A 表引用 B 的 id」这种跨文件引用,**引用完整性必须有闸**,不能靠人对——就是 `check_guide.py` 闸④,
    并配反证测试(喂事故当天那张表 → 必须报出 35 处违规)。
  - 验收脚本改成浏览器启动前先断言:表里每个 id 都能在**真实内容**里查到,查不到直接退出,
    不让后面几十项断言粉饰。脚本头部注释也把这段教训写死在那里了。
  - **写验收脚本时自问一句:「如果被验证的东西根本不存在,这个脚本会红吗?」答不出来就是假绿。**
- 已进记忆:`[[verify-target-must-be-real-content]]`。

### ② diff 类闸必须 commit 之后跑,commit 前跑扫的是上一笔

- **现象**:本地跑棘轮闸 / 缓存破闸绿油油,push 上去 CI 红。
- **根因**:这两个闸默认比的是 `HEAD~1..HEAD`。**commit 之前跑,`HEAD` 还是上一笔**,
  扫的是上一笔的 diff,和你手上这堆改动毫无关系。
- **怎么防的**:`check_line_ratchet.py`、`check_cachebust.py`、`check_blob_size.py` 这三个
  diff 类闸,**一律 `git commit` 之后、`git push` 之前跑**。要在 commit 前跑就得自己带
  `--base` / `--head` 指对范围。文件类闸(`check_file_size.py`、`check_guide.py`)不受影响,
  它们看的是工作区当前状态。

### ③ 改了产物忘了 bump `?v`,用户浏览器一直吃旧包

- **现象**:`b72714df` 那笔 CI 红,红在 `lint-size` 的「缓存破机械闸 · 产物变则源 HTML ?v= 必 bump」。
- **根因**:改了 `static/dist/main.js` 之类的产物,但 `home.html` 里引它的 `?v=` 没跟着改。
  用户浏览器认那个 query 串做缓存键——不改就一直吃旧包,**上线了等于没上线**。
- **怎么防的**:`scripts/check_cachebust.py` 已经是 CI 硬门(2026-07-10 事故固化)。
  正确做法是产物一动就把 `home.html` 里那几个 `?v=` 一起 bump。这次是
  `12011801` → `12017001`,三处一起改:`home.css`、`i18n-data.js`、`main.js`。
- **顺带一条**:这个闸曾经漏守主站 CSS,两天内重演了同一种病——**清单式的闸必须配覆盖率测试**,
  否则它会「报绿」而其实压根没看那个文件。

### ④ lint 要跑全仓,只跑改动文件会漏

- **现象**:`890b1a14` 的 CI,九个 job 里八个绿,`lint (black + ruff + prettier + eslint)` 红。
  紧接着补了 `621639e2`「black 重排教程闸的覆盖率测试」。
- **根因**:push 前只对改动的前端文件跑了 prettier,**没跑 black**。新加的
  `tests/unit/test_guide_gate.py` 是 Python,black 不满意。CI 的 lint job 跑的是全仓。
- **怎么防的**:push 前**跑全仓的 lint,四个都跑**(black / ruff / prettier / eslint),别按改动文件挑。
  记住 `ruff ≠ black`——ruff 查的是 pyflakes 类真 bug,格式化的唯一权威是 black。

### ⑤(附带)CI 的 `cancelled` 不是绿

- **现象**:`890b1a14` 那次 run 的整体 conclusion 是 `cancelled`。
- **根因**:workflow 配了 `concurrency: cancel-in-progress`,同一个 ref 上有新 push 就把旧 run 取消。
  紧接着 push 的 `621639e2` 把它掐了。
- **怎么防的**:判绿只认 `conclusion == success`,并确认**自己那笔 commit 是那个绿 run 的祖先**。
  `cancelled` 既不是绿也不是红,得往下一个 run 看。这次 `621639e2` 的 run 里
  `lint-guide` / `lint-size` / `lint-ui` / `lint` 全绿,`890b1a14` 是它的祖先,所以这批算过了。

### 7.3 UI lint 补全后暴露的 33 处存量债

`scripts/ui_design_lint.mjs` 原来只认 `max-width: NNNpx`,认不出**层叠结果逐像素相同**的两种等价写法
`width: min(100%, NNNpx)` 和 `max-width: min(NNNpx, 100%)`。只认一种的闸,等于在
「考验作者会不会换写法」。补全探测器之后,原本就写在库里的 34 处一次性现形。

其中教程页自己新写的那一处(`static/home-57-guide.css`)当场清掉了,改成「容器铺满 +
段落 `max-inline-size` 限测量宽」——**版面宽和阅读行宽是两回事,限行宽是对的,限版面宽是 bug**。
剩下 **33 处**是别的模块的用户可见版面,超出这批范围,原样欠着,已登记在
`scripts/ui_lint_baseline.json` 的 `_notes` 里(基线从 120 → 153),逐处清单在
`docs/ui/UI_LINT_REPORT.txt` 的「小固定max-width」小节。

按模块分布(我从提交 diff 里逐条数的,合计正好 33):

| 模块 | 处数 | 具体文件 |
| --- | --- | --- |
| `/ai` | 17 | `ai-intake.css` 4、`ai-review-jc.css` 3、`ai-client-empty.css` 2、`ai-client.css` 2、`ai-desk.css` 2、`ai-pkg.css` 1、`ai-profile.css` 1、`ai-recon.css` 1、`ai-shell.css` 1 |
| `/dms` | 8 | `dms-intake.css` 2、`pick.html` 2、`dms-billing.css` 1、`dms-roster.css` 1、`dms-shell.css` 1、`dms-util.js` 1 |

| `console` | 2 | `console.css` 2 |
| 其他 | 1 | `static/erp-mrerp-connect.css` 1 |

**我的判断,供你拍板:清这 33 处的时候,该先分类,不该一刀切改成铺满。**

看具体命中就明白了:里头相当一部分是**弹窗**(`.casg` 客户分配弹窗、`purm` 采购弹窗、
`dms-util.js` 里那个 400px 的 toast/dialog)和**空态卡**(`ai-client-empty.css` 的 560/360、
`workspace-gate-html.ts` 那句 380px 的说明文字)。弹窗和空态**本来就该有宽度上限**——
一个登录框在 27 寸屏上铺满 2560px 是灾难,不是「响应式」。规则想拦的是**内容区版面**在宽屏留大片空白,
不是所有的固定宽度都有罪。

所以清债建议按三类走:
1. **内容区版面**(表格页、列表页、正文区)→ 真违规,改成铺满。
2. **弹窗 / 抽屉 / 空态卡 / 段落测量宽**→ 大概率不是违规,应该给规则加白名单机制
   (比如选择器命中 `.modal` / `.dialog` / 空态类,或者显式的 `/* ui-lint-ok: 弹窗宽度上限 */` 注释)。
3. **拿不准的**→ 真浏览器上宽屏看一眼再定。

现在的探测器只看 CSS 文本,不看那段 CSS 用在什么元素上,所以第 2 类会一直误报。
在加白名单之前硬清,会把好设计改坏。**基线目前是「只许降不许升」——这 33 处还欠着,但不许再添新的。**

理由:纯拍板,零成本,但它是整份手册所有排查路的终点。现在那个终点是空的。

**7. UI lint 白名单机制,再清那 33 处债(7.3)。**
理由:不急,但**别在加白名单之前硬清**,会把弹窗和空态改坏。先给规则一个「弹窗 / 空态豁免」出口,
再按三类分批清。基线已经锁住了不许再添新的,债不会继续涨。

**8. 给「标题动词开头」补一条机械闸。**
理由:四条死因里,这一条现在**唯一没有机械闸兜底**。以后加章、别人接手写别的手册时,
它是最容易悄悄退化的一条。一条扫 `title.zh` 首字的正则就够。
