## 二、真账套取证(推翻了多条写在代码里当事实传的判断)

**这些是从 `\\accserver\ACCOUNT` 与 `\\192.168.0.212\pas212` 的真账套读出来的,别再靠推演改回去。**

   所以新建品当次卖出确实没有成本基础(不许编),但「有档零库存」的品有标准成本可用。

## 三、★ 软删行 P0(今天最重要的发现)

### 现场

真实客户账套 `69EXP/TEST`,同一张销售票 `IV69/00473` 连推三次,**每次都回报成功并给出单号
`IV690531-001`**,Express 里查无此单,账套目录 8 张表**一个字节没动**(mtime 全停在 12:23:30)。

### 根因

**DBF 的删除是打标记不是物理删除。** 会计在 Express 里删掉那张单后,行还躺在 ARTRN 里:

```
行0  已删除=True  DOCNUM='IV690531-001'  YOUREF='IV69/00473'  CUSCOD='ก001'  NETAMT=0.0
```

`dbf_sales._find_existing` 直接遍历全表、**没有 `is_deleted` 判断** → 幂等闸在软删行上命中 →
返回 `ok=True / skipped=True` + **那条旧行的旧格式 DOCNUM**,一个字节不写。

**这同时解释了「为什么单号不是真实票号」** —— 真实票号功能(`_sales_docnum`)本来就是对的
(`IV69/00473` 10 字节 ≤ DOCNUM 的 C(12)),显示的 `IV690531-001` 是幽灵行的旧号盖住了。

### 只修幂等闸不够 —— 还有两堵墙

| 墙 | 位置 | 不修会怎样 |
|---|---|---|
| ② 读回校验 | `dbf_sales._verify` / `dbf_writer._verify`(ARTRN/GLJNLIT/ISVAT) | 销项 DOCNUM=票面票号,删单重推时新旧同号,旧行被一起累加 → 判借贷不平 → **把刚写好的好单整单回滚** |
| ③ 明细校验 | `dbf_detail.verify_detail` | 旧 STCRD 明细也数进来 → 行数对不上 → 回滚 |

### 顺带揪出的静默烂账(不报错)

- `stock_sale.write_stmas_fields` 扣库存**扣到幽灵行**,真档一动不动 → 账实不符
- `_update_arbal` / `_update_apbal` 把余额加到 Express 看不见的行 → 客户余额凭空少一截
- `master_create._find_code` 复用已删客户码 → 单据挂到 ERP 里列不出来的对手方

### 修法

判据收口成 **`dbf_schema.live_rows(table)`**,docstring 写死分界:

- **「这条业务记录还算不算数」→ 排除软删**(18 处中的 15 处)
- **「这个号用没用过」→ 保留软删**(`_next_docnum` / `_next_code` / `_next_stkcod`)——
  跳过会把删掉那张单的号再发一次

变异验证:去掉 `live_rows` 的软删判断 → 合成 13 红 + 真账套 2 红,而三条发号用例照样绿
(证明两类判据确实分开了)。

### 给云端的新钩子(**下一批要接**)

小助手 ack meta 新增 **`duplicate_skipped`**(加法式,旧云端无感):

| meta | 含义 | 云端该显示 |
|---|---|---|
| `false` | 真写了一张新单 | 「已写入 ERP · 凭证号 X」 |
| `true` | 幂等命中,**什么都没做** | 「ERP 里已有同票号单据 X,本次未重复写入」+ 给「去 ERP 核对」动作 |
| 字段缺失 | 旧版小助手 | 回落现有展示 |

**此前两者在云端物理上分不出来**(都是 `ok=True` + 有单号),现场连报三次成功没人看出来,根子在这。

## 四、新规则:选了库存就一定能落(Zihao 拍板)

选「库存」后三种情形**都不再 escalate**:

| 账里状况 | 做什么 | COGS |
|---|---|---|
| 有这个品 + 正库存 | 扣库存(逐字未动) | 移动均价 |
| 有这个品 + 零/负库存 | **卖成更负** | `STNPR`>0 按标准成本;否则不结转(`reason=no_cost_basis`) |
| 账里没这个品 | **建 STKTYP=0 + 卖成负** | 无成本基础 → 不结转(`reason=new_item_no_cost_basis`) |

**唯一剩下的 escalate**:账套还没配存货科目组。

### 为什么这么改 —— 别再改回去

07-24 曾拍「分支③ 改 escalate」,理由是「建壳后库存恒 0,下一单必卡,是死循环」。
**允许卖负之后这个理由不存在了**(下一单不会卡,只会更负),前提被换掉,不是推翻拍板。

### 三条诚实线(硬要求)

1. **绝不编成本** —— 没有成本基础就是不结转 COGS。禁止售价倒推毛利、禁止默认成本。
2. **绝不静默** —— 新建了库存品 / 未结转成本必须在推送日志显性标出(已做:琥珀标记 + 说明)。
3. **可捞回** —— 推送日志有「未结转成本」筛选项(`push_log_meta` 是判据单一源,SQL 与卡片共用)。

⚠️ 现实提醒:`70EXP` 里 162 个库存品**只有 2 个有标准成本**,所以「有档没货」实际大多走不结转分支,
未结转成本的单量会不小 —— 捞回清单是刚需不是可选。

## 十二、★★ 本窗口的方法论教训(比代码更重要)

### 1. CSS 属性生效 ≠ 效果生效

查看器 sticky 我只断言了 `getComputedStyle(...).position === 'sticky'` —— 属性确实对,
但祖先链上 `.dx-card` 与 `.dx-acc-item` 两处 `overflow:hidden` 把它们变成滚动容器,
sticky 只相对那个盒子生效,而它们自己不滚。**实测滚 600px:top 从 549 掉到 -46,与不加 sticky 分毫不差。**

用户一眼看出来,我的验收 51/51 全绿。

> **接手请守**:凡「位置/跟随/吸附/滚动」这类**空间行为**,断言必须量真实坐标(滚动前后
> `getBoundingClientRect()`),不能只断言 CSS 属性值。修法是 `overflow:hidden` → `overflow:clip`
> (同样裁圆角,但不建立滚动容器)。

### 2. 闸报绿 ≠ 闸看过 —— 清单式闸必须有覆盖率测试

改了 `static/dist/home.css` 没 bump `?v`,缓存破闸照报 PASS —— 因为 `CACHE_BUST_PAIRS` 里
**压根没有主站 CSS 这一行**。这个闸自己的注释就写着这条病(`ai.js` 曾连续 5 次改动 `?v` 停在 79),
两天后又在 `home.css` 上重演。

补法:清单改成按入口页派生(五个入口 27 对),并加**覆盖率测试** —— 入口页里每个指向仓库内文件的
`?v=` 引用都必须在清单里有一行。这条测试当场揪出 **15 处没守的**,其中 `pearnly-ui.css` 被五个入口
共用(漏 bump = 五个站一起吃旧样式)。

> **接手请守**:仓库里还有别的清单式闸(`check_file_size` 的监控清单、`push_exception_classify`
> 的码清单、`erp-log-card` 的 i18n 码表)。同样的病随时会在它们身上重演,值得照此加覆盖率测试。

### 3. 跨边界接缝 —— 一天犯了五次

昨天记了三次,今天又两次(`ThaiInvoice` 吃掉溯源 / 前端不认 `PRIOR_DOC_STILL_IN_ERP`)。
病根一样:**两头都写对了,中间那一段没人负责验**。

今天的做法是每条缝都补一条**从真实数据形状出发**的端到端测试(`test_roundtrip_provenance_seam`、
`test_prior_doc_seam`、`test_erp_unit_guessed_seam`),并对每条都做变异验证(拆掉任一段 → 立刻红)。

### 4. build 与 bump 的顺序

正确顺序:**改源 → bump `?v` → `npm run build` → 提交(dist 一起)**。
反过来会让 `static/dist/home.html` 里留着旧指纹,CI 重建即报「dist 与源不一致」。今天红过一次。
